# PUSH-SPEC — напоминания о дедлайнах при закрытом приложении

Статус: спека Fable 2026-07-19, утверждённое направление (пуши = флагман платного
П1, выместили календарь). Механику кодит Opus по этой спеке; UX-слой (настройки,
вид уведомлений, permission-флоу) — Fable в П1. Читать вместе с SYNC-SPEC.md
(идентичность данных) и ANDROID-PRENOTES.md (TWA).

## 1. Цель и рамки

Задача с дедлайном должна НАХОДИТЬ пользователя, а не ждать открытия приложения:
системное уведомление на телефоне/десктопе при закрытом DUSK. Это закрывает
главную продуктовую дыру таск-менеджера (pull-обзоры уже есть трижды: сортировка,
бейджи, дайджест «Грядущее»; push-канала нет вообще).

Жёсткие ограничения (те же, что у синка): ноль цены, без своего always-on
сервера, полный оффлайн-корректный локал, интернет любой (не LAN). Всё
укладывается: Web Push + существующий Cloudflare Worker (`worker/`,
dusk-sync.petrehundima.workers.dev) + бесплатный CF cron + KV.

Платформы: Android (Chrome/TWA — надёжно), Windows desktop Chrome (работает при
запущенном браузере). iOS вне рамок (не наш кейс).

## 2. Архитектура (вид сверху)

```
[клиент DUSK] --при каждом sync + при изменении дедлайнов--> PUT /push/schedule
     |                                                        (Worker KV)
     +--одноразово: PushManager.subscribe(VAPID)--> POST /push/subscribe
[Worker cron каждые 5 мин] -> скан расписаний в KV -> due-записи ->
     Web Push (VAPID JWT + RFC8291 aes128gcm) -> все подписанные девайсы
[sw.js] 'push' -> showNotification(готический вид) ; 'notificationclick' ->
     открыть/сфокусировать приложение + скролл к задаче (hash с uid)
```

Ключевая идея: **worker не знает про Google Drive и не хранит state** — клиент
сам приносит ему маленькое расписание ближайших дедлайнов. Расчёты «что и когда
напомнить» делаются на клиенте (там весь движок повторов), worker только
«будильник + почтальон».

## 3. Идентичность: syncId

Пуш-данным нужен ключ, общий для всех устройств одного человека. Аккаунтов нет —
используем **syncId**: `crypto.randomUUID()`, создаётся при первом включении
пушей, живёт в синкуемом state (`state.pushProfile.syncId`) → через Drive-синк
доезжает до всех устройств автоматически. KV-ключи: `push:<syncId>`.
Ротация (сброс в настройках) = новый uuid, старая запись протухает по TTL.

## 4. Данные в KV (одна запись на syncId)

```jsonc
// key: push:<syncId>   (KV, TTL 60 дней, продлевается каждым PUT)
{
  "devices": [ // подписки Web Push, максимум ~5
    { "deviceId": "uuid", "endpoint": "...", "keys": { "p256dh": "...", "auth": "..." },
      "label": "Pixel 7", "addedAt": 0, "lastOkAt": 0 }
  ],
  "schedule": [ // ближайшее окно, строится клиентом; cap 80 записей / 21 день
    { "id": "uid-задачи:offset", "uid": "...", "title": "Отчёт кровью",
      "at": 1760000000000, "kind": "lead24h" | "due" | "overdue-once",
      "firedAt": 0 } // 0 = ещё не стреляло; cron ставит timestamp
  ],
  "prefs": { "tzOffsetMin": -180, "quiet": { "fromMin": 1380, "toMin": 480 },
             "offsets": [86400000, 0], "titles": true },
  "updatedAt": 0
}
```

- `titles:false` — параноидальный режим: пуш без названия задачи («Задача близка
  к сроку») — приватность не приоритет, но опция дешёвая.
- `firedAt` в KV = дедуп: одна запись стреляет ОДИН раз, даже если cron
  перезапустился; letят пуши на ВСЕ девайсы (напоминание нужно везде).
- Индекс для cron: ключ `push:_index` = массив syncId (worker поддерживает при
  subscribe/unsubscribe). Личное использование — единицы записей, скан дёшев.

## 5. Endpoints worker'а (добавка к OAuth-прокси; тот же ALLOWED_ORIGIN)

- `POST /push/subscribe` { syncId, device } → upsert девайса + в индекс.
- `POST /push/unsubscribe` { syncId, deviceId } → выкинуть девайс; пустой
  devices → снять из индекса.
- `PUT /push/schedule` { syncId, schedule, prefs } → перезаписать расписание,
  СОХРАНИВ firedAt совпадающих id (иначе после каждого синка всё стреляло бы
  заново). Мерж по id: новый список — источник истины состава, firedAt — из
  старого.
- Auth поверхности: endpoints принимают только запросы с ALLOWED_ORIGIN (CORS,
  как /exchange), rate-limit по IP не нужен (личное). syncId в теле — bearer
  фактически; угадать uuid нереально. Достаточно для нашей модели угроз.

## 6. Cron (`scheduled` handler, каждые 5 минут)

1. Читает `push:_index`; для каждого syncId — запись KV.
2. `due = schedule.filter(e => !e.firedAt && e.at <= now)`.
3. Тихие часы: если сейчас внутри quiet-окна (по tzOffsetMin) — `kind!=='due'`
   откладываются до конца окна (просто не стреляют, at не двигаем; поймаются
   первым cron'ом после окна). `due`-момент — стреляет всегда (это будильник).
4. Отправка каждому девайсу; 404/410 от push-сервиса → девайс выкидывается.
5. `firedAt = now`, запись обратно в KV (одна запись — один write; батч).
6. Просроченный хлам: `at < now - 48ч` и не fired → пометить fired (не будить
   среди ночи неделей позже).

## 7. Web Push криптография (⚠ самая сложная часть — Opus, аккуратно)

Workers runtime без Node-библиотек, всё на `crypto.subtle`:
- **VAPID**: ES256 JWT (aud = origin эндпоинта, exp ≤ 24ч, sub = mailto).
  Ключевая пара генерится один раз (wrangler secret: приватный; публичный —
  константа клиента для subscribe `applicationServerKey`).
- **Payload**: RFC 8291 aes128gcm (ECDH P-256 + HKDF). Есть проверенные
  референс-реализации под Workers (искать «web-push cloudflare workers subtle»);
  НЕ изобретать, портировать с тест-векторами RFC 8291 Appendix A в vitest.
- Пустой payload — законный фоллбэк Ф1 (уведомление «есть напоминание» без
  текста, sw дотягивает детали из IDB) — позволяет разнести крипту и продукт.

## 8. Клиент

- **Построение расписания** (чистая функция, vitest): по state.tasks →
  ближайшие 21 день: для каждого дедлайна offsets из prefs (default [24ч, 0]);
  повторяющиеся — ОДНО следующее вхождение (движок повторов уже есть; помнить
  урок B6-06: границы дня локальные `_ymd`, не toISOString-UTC). overdue-once:
  один раз через 1ч после просрочки, если не выполнено.
- **Когда шлём PUT**: после каждого успешного syncNow (расписание из
  СМЕРЖЕННОГО state) + троттлинг-дебаунс 30с на локальные правки дедлайнов
  онлайн. Оффлайн-правки доедут со следующим синком — eventual, принято
  (устройство с уставшим расписанием может прислать пуш по старому дедлайну;
  редко и самочинится следующим синком).
- **sw.js**: `push` → `showNotification(title, { body, tag: e.id, icon:
  готическая иконка, data: { uid } })`; tag = дедуп на девайсе.
  `notificationclick` → focus/открыть `/#task=<uid>` → скролл+пульс
  (переиспользовать railDigestGo-механику). Бамп CACHE не нужен (sw логика,
  не precache-список), но версию sw поднять.
- **Настройки (UX — Fable П1)**: панель в «Данные»/отдельно: тумблер включения
  (permission-флоу с объяснением ДО системного промпта), список устройств
  (label + убрать), offsets-набор, тихие часы, titles-тумблер, «проверить»
  (тестовый пуш). Вид уведомления — готический (иконка-бейдж, формулировки).

## 9. TWA-стыковка (важно ДО сборки APK)

Web Push в TWA работает через Chrome автоматически — уведомления выглядят
нативно. В ANDROID-PRENOTES добавить: (а) не резать notification-разрешение в
манифесте TWA; (б) проверить пуш на закрытом TWA в первом же смоке APK;
(в) заодно manifest `shortcuts` («Новая задача») и Share Target — тот же файл
manifest.json, одна волна правок.

## 10. Фазы (каждая — отдельный коммит+пуш, тесты зелёные)

- **Ф1**: worker endpoints + KV-схема + cron-скелет + отправка ПУСТОГО пуша
  (без payload-крипты) + клиентский subscribe + расписание-билдер с vitest +
  sw 'push'-хендлер с фоллбэк-текстом. Уже даёт рабочие напоминания!
- **Ф2**: RFC 8291 payload (тест-векторы RFC в vitest) → полные тексты.
- **Ф3**: notificationclick deep-link, тихие часы, overdue-once, устройства-CRUD.
- **Ф4 (Fable П1)**: настройки-UX, готический вид, permission-флоу, полировка.
- **Ф5**: хардening: протухшие девайсы, ротация syncId, двухдевайсный ручной
  прогон, лимиты (KV writes: 1 PUT/синк — далеко от 1k/день).

## 11. Риски/решения

- Крипта RFC 8291 руками — главный риск → изолировать в модуль с тест-векторами
  (Ф2), Ф1 живёт без неё.
- Двойной пуш при гонке cron'ов — KV не транзакционен; окно 5 мин, личное
  использование: принято (tag на девайсе дополнительно дедупит показ).
- Уставшее расписание оффлайн-девайса — eventual, самочинится синком (§8).
- Notification-пермишен отклонён — фича тихо выключена, тумблер объясняет как
  вернуть (настройки сайта).
