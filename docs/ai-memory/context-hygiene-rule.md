**⭐ ЖЕЛЕЗОБЕТОННОЕ + ОБЯЗАТЕЛЬНОЕ ПРАВИЛО ~150к токенов (юзер 2026-07-19,
переуточнено). Явное, но НЕ ограничивающее. Пять частей:**

**а) ЯВНЫЙ ОРИЕНТИР.** В идеале примерно **каждые ~150к токенов** — чекпоинт +
очистка контекста (/clear). Это ЦЕЛЬ-ориентир, держать в голове.

**б) НЕ СТРОГОЕ — НИКОГДА НЕ ОГРАНИЧИВАЕТ РАБОТУ.** Правило совершенно НЕ должно
влиять на исполнение задачи. Задачу делать с **максимально качественным, глубоким
и объёмным результатом БЕЗ оглядки на контекст** (если юзер явно не затребовал
обратное). Категорически НЕ резать глубину/объём/качество/тщательность, НЕ
обрывать единицу работы, НЕ спешить закрыть раньше из-за счётчика, НЕ использовать
«гигиену» как повод не делать/сократить работу (ОШИБКА этой сессии — так делать
НЕЛЬЗЯ). 150к можно превышать сколько нужно. Порог сдвигает ТОЧКУ ОЧИСТКИ, а не
объём/планку работы.

**в) МЕХАНИЗМ — СВЕРКА СЧЁТЧИКА В КОНЦЕ ЕДИНИЦЫ РАБОТЫ (не раньше).** Завершив
единицу работы как надо, СВЕРИТЬ **реальный** израсходованный контекст по счётчику
(см. г — он теперь виден). Действовать ТОЛЬКО если ВСЕ условия разом:
  1. ориентир 150к **настигнут или очень близко**, И
  2. чекпоинт можно сделать **ПРЯМО СЕЙЧАС без каких-либо неудобств, недостатков,
     проблем и негативных последствий для качества** (т.е. работа в цельной точке,
     не в середине связки правок).
Тогда → чекпоинт + подготовить всё к /clear + дать хэндофф-промпт. **Если 150к
далеко — НЕ чекпоинтить, продолжать работу.** Завершение единицы работы САМО ПО
СЕБЕ НЕ триггер — триггер это счётчик ≥ порога. Не путать «доделал кусок» с «пора
чистить».

**г) НИКОГДА НЕ ГАДАТЬ ЧИСЛО — ЧИТАТЬ СЧЁТЧИК.** Урок 2026-07-19: без счётчика я
был слеп и утверждал «не близко к 150к», будучи на ~270к. Теперь настроено
(`~/.claude/settings.json`, глобально):
  - **`totalTokensReminder: "countdown"` + `totalTokensReminderAfterUserTurn: true`**
    — нативный блок `<total_tokens>N tokens left</total_tokens>` после каждого
    tool-результата и юзер-хода (оставшиеся токены окна);
  - **UserPromptSubmit-хук** `node ~/.claude/ctx-tokens.mjs --hook` — вливает мне
    строку «КОНТЕКСТ: ~Nk токенов…» каждый ход (число = input+cache_creation+
    cache_read из последнего usage транскрипта = текущая занятость окна);
  - **статуслайн** `statusline-combo.mjs` (caveman + `ctx ~Nk/150k`) — цифра юзеру.
  Активация проводки после reload (`/hooks`) или рестарта; статуслайн — почти
  сразу. Скрипты пайп-тестами ПРОВЕРЕНЫ. Если счётчика в контексте нет (не
  подхватился) — сказать юзеру, не гадать.
  **ФИКСЫ 2026-07-22 (лимиты были неактуальны/дробные):** кэш лимитов теперь
  **по session_id** (`_usage-cache-<sess>.json`) — параллельный сеанс Claude Code
  больше НЕ перетирает числа этой сессии (особенно cost_usd); проценты
  **округляются** (`Math.round`) в хуке и статуслайне; в кэш пишется `ts`, и хук
  помечает `⚠данные лимитов ~Nмин назад`, если снапшот старше 120с (видимая
  устарелость вместо молчаливой). Числа в хуке — всё равно на 1 рендер статуслайна
  позади (live rate_limits в stdin хука НЕ приходят — только через кэш статуслайна).

**д) ОЧИСТКА — ТОЖЕ НЕ БЕСПЛАТНА; 150к = ТОЧКА ОЦЕНКИ РАЗМЕНА, НЕ АВТО-СБРОС**
(уточняющий анализ, юзер 2026-07-19). `/clear` платит «налог холодного старта»:
новая сессия перечитывает CLAUDE.md, память, ключевые исходники, восстанавливает
состояние. На многосессионном проекте этот налог × число сессий достигает
десятков-сотен тысяч токенов — иногда БОЛЬШЕ, чем экономит очистка. Значит очистка
= РАЗМЕН (bloat-издержка продолжения ↔ re-read-налог след. сессии), НЕ чистый
выигрыш. **Цель — минимизировать СУММАРНЫЕ токены проекта (все сессии), а не
занятость одного окна.** Отсюда в точке ~150к (оценка, не авто-/clear):
  1. **Сперва минимизировать re-read-налог, а не рефлекторно чистить.** Лучший
     рычаг — компактный самодостаточный хэндофф (память + топик-файл + короткий
     триггер), чтобы след. сессия читала СЖАТУЮ сводку, не пере-выводила из
     исходников. Хороший хэндофф → очистка дёшева; плохой → дорога. Готов такой
     хэндофф + единица закрыта → чистить на 150к нормально.
  2. **Когда re-read неизбежно дорог** (задача по природе требует много живого
     несжимаемого в память исходника/контекста) ИЛИ **ты в середине цельной
     единицы у самой границы коммита** → ОСМЫСЛЕННО ПОДНЯТЬ порог: продолжать за
     150к до естественной, хорошо задокументированной точки. Не догма «ровно 150».
  3. **Прикидка размена:** оценить (re-read-налог свежей сессии) против
     (bloat-издержка продолжения до след. естественной границы). Чистить когда
     хэндофф компактен И единица закрыта; продолжать/поднять порог когда единица
     почти закрыта ИЛИ пере-вывод дороже разбухания. 150к — сигнал «стоп-оценить
     размен», не курок сброса.
Связь с б/в: (б) порог не режет работу; (в) триггер = счётчик в конце единицы;
(д) сам триггер — не авто-действие, а развилка «чистить ↔ поднять порог» по
дешевизне хэндоффа и стоимости пере-вывода.

**⛔ ХЭНДОФФ-ПРОМПТ — ОБЯЗАТЕЛЬНО ВЫВЕСТИ В ОТВЕТЕ готовый-к-вставке блок
(юзер 2026-07-22 поймал: я подготовил док, но НЕ выдал сам промпт).** Чекпоинт
считается сделанным ТОЛЬКО когда в ответе есть вставляемый триггер-блок (в
```-фенсе или явно выделенный), который юзер копирует в новую сессию — НЕ док,
НЕ саммари-сообщение, НЕ ссылка на файл. Если работа И план полностью завершены —
промпт не нужен, явно сказать «завершено».
**⚠ ОДИН ИСТОЧНИК ИСТИНЫ (юзер 2026-07-22): формат хэндофф-промпта живёт ТОЛЬКО
здесь, в этом правиле.** Порог-хук `ctx-tokens.mjs` НЕ дублирует формат — он только
ТРИГГЕР+указатель: «на пороге выполни чекпоинт-ритуал по context-hygiene-rule,
формат — там». (Почему раньше игнорировал правило: память = фоновый контекст, я
шёл по гисту «хэндофф»→«док» вместо точной клаузы; форсирующей функции на действие
не было. Фикс: неизбежный per-turn хук-указатель гонит СЮДА исполнять, а не
пересказывать по памяти.) Не копировать эти 4 пункта в хук/иные места — дрейф.
**Формат — ТРИГГЕР, НЕ пересказ состояния**
(после /clear память MEMORY.md + активный topic-файл грузятся АВТОМАТИЧЕСКИ →
дублировать «сделано/осталось» в промпт ВРЕДНО: лишние токены + два источника
правды → дрейф). Состояние держать ТОЛЬКО в памяти (обновлять каждый батч/единицу).
Промпт короткий, но исчерпывающий, без шума и дублей — делает 4 вещи:
1. **Порядок чтения файлов** (CLAUDE.md → topic-память плана «там сделано+ОСТАЛОСЬ»
   → нужные repo-доки/спеки/превью).
2. **Скилл-цикл обязателен** (одной строкой).
3. **Немедленный следующий шаг** (взять след. пункт из «ОСТАЛОСЬ»; приоритет
   неочевиден — назвать дефолт + «спроси юзера»).
4. **Неочевидные правила, легко пропустить** (ритуал верификации/бампа version/
   коммита-поимённо/пуша/ревью-на-проде; «развилку/новый глиф без вердикта —
   спрашивать, не выдумывать»).
Цель: ~⅓ от «подробного»; полнота НЕ теряется (делегируется авто-грузящейся памяти).

**Why:** после /clear выживают только файлы (память, доки репо, git) — всё, что
осталось лишь в контексте разговора (незаписанные находки, замеры, уроки,
договорённости), теряется безвозвратно.

**How to apply (в конце единицы работы):**
1. Свежие решения/находки/уроки → память (topic-файл + строка в MEMORY.md) или
   repo-доки (REVIEW-QUEUE.md, планы). Обновлять КАЖДУЮ единицу — независимо от
   порога (это дёшево и спасает от потери).
2. Незакоммиченное → commit+push ([[auto-commit-push-after-work]]).
3. Открытые хвосты явно в topic-памяти («ОСТАЛОСЬ: …»).
4. СВЕРИТЬ счётчик (г). Порог достигнут + без ущерба → чекпоинт+хэндофф+«к /clear
   готово». Иначе → продолжать работу.
